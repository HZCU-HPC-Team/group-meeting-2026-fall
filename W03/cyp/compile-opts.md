# 编译优化实验（不改一行代码，只换编译选项）

## 1. 实验设计

- **变量只有一个**：编译选项。源码 `pivot.c` 一个字节没动，输入文件没动（手册第 4 条：输入不可修改）；
- **档位**：`-O0 / -O1 / -O2 / -O3`，再加两档 `-march=native`（本机 = Raptor Lake，会启用 AVX2 等指令集）；
- **每档 3 次**，取均值，同时记录离散程度（看噪声有多大）；
- **判据**：每次换档都重新 `diff result.txt refer-2dim-5h.txt`——**结果变了就不算数**，加速比没有意义；
- **计时口径**：手册规定以程序打印的 `Using time` 为准（不含读写文件、不含启动），所以下表主口径是"程序自报 ms"，外面 wall 只做对照。

规模：`dim=2, n=500, k=2` → 组合数 `C(500,2) = 124750`，每组内层 `n²·k = 500000` 次比较。

**环境**（本机，非服务器）：

| 项 | 值 |
|---|---|
| 机器 | 笔记本，13th Gen Intel Core i7-13650HX（14 核 20 线程，基频 2.6 GHz） |
| OS | Windows 11 (10.0.26200) |
| 编译器 | GCC 16.2.0（w64devkit / mingw-w64） |
| 命令 | `gcc <flags> -o pivot_<level>.exe pivot.c -lm` |
| 运行 | `.\pivot_<level>.exe .\uniformvector-2dim-5h.txt`（单线程） |
| 负载 | 后台有系统/聊天软件常驻，未做完全静默；这是 O0 档波动 ±1.5% 的主要原因 |

## 3. 正确性：18 次运行，18 次结果完全一致

`result.txt` 每次 2000 行（1000 max + 1000 min），与 `refer-2dim-5h.txt` 逐字节比对（CRLF 归一化后 SHA-256）：

```
REF  924858624d0290f1  lines=2001
...
18/18 files identical to refer (CRLF-normalized)
```

> 说明：Windows 上 `fprintf("\n")` 会写成 CRLF，仓库里的 refer 是 LF，所以**直接 `diff` 会全红**——这不是算错了，是行尾差异。校验脚本先做 `\r\n → \n` 归一化再比哈希（`data/` 之外的 `verify_results.py` 逻辑就三行）。

**这一步是本周最重要的纪律**：0.21 → 1.89 G iter/s 的加速比，只有在 18/18 结果不变的前提下才成立。

## 4. 数据说明了什么

### 4.1 加速主要发生在"`-O0 → -O1`"这一步，而不是"越优化越快"

- `-O0` → `-O1`：**9.16x**。这一步 GCC 做了三件事：把 `pow(x, 2)` 折成 `x*x`（`-O0` 下它是真的 libm 调用，一共 `n·k·dim × 组合数 ≈ 2.5×10⁸` 次）、把 `SumDistance` 内联进 `Combination`、把 `rebuiltCoord` 的地址计算提到循环外；
- `-O1 → -O2`：**反而慢了约 13%**（33.0 s → 37.2 s）；
- `-O2 → -O3`：又快了约 11%（37.2 s → 33.3 s）。

`-O2` 比 `-O1` 慢是个**反直觉但可复现**的结果（同机 3 次，离散很小）。合理猜想：内层是"`max` 链 + 浮点累加"这种强串行依赖结构，`-O2` 打开的某些优化（循环展开/向量化试探）改变了指令调度，反而拉长了依赖链上的等待；`-O3` 换用更激进的展开与调度后又补回来了。**这条要在服务器上用 `perf stat` 的 IPC 和 `perf annotate` 才能坐实**——这正是下周上机要验证的点，见 [perf.md](perf.md)。

### 4.2 `-march=native` 在本例是负收益

`-O2 -march=native`（7.90x）比 `-O2`（8.13x）慢，`-O3 -march=native`（7.51x）比 `-O3`（9.09x）慢 17%。

原因同样是"这个内层循环不吃 SIMD"：它没有可向量化的规约（`chebyshevSum += max(...)` 是标量累加），启用 AVX2 后编译器尝试用 `vmaxsd`/shuffle 反而引入额外指令与跨域延迟。**结论：不要迷信 `-march=native`，它只对能向量化的循环才划算**；要证明也得靠 perf 的 instructions 计数对比。

### 4.3 加速比的天花板很低

- 官方口径下 `-O0` 302.6 s，最好一档 33.0 s；
- 但算法复杂度一点没变：还是 `C(n,k) × n² × k` 次比较，只是每次比较的常数从"约 22 ns"降到"约 0.53 ns"；
- 赛题的时间上限要求是"几分钟级"，这份 baseline 在服务器上 `-O0` 只会更慢（服务器主频通常低于这颗 2.6 GHz 的移动端高睿频，但核多——而 baseline 是单线程，多核用不上）。

**所以编译选项是"第一次白捡的 9 倍"，之后就没了**。要再快一个数量级，只能动算法（复用重建坐标、只算 `i<j`、`O(n²)→O(n log n)`）或用并行（128 核）。方向见 [perf.md](perf.md) 第 6 节。

## 5. 复现方式

```bash
# Linux（服务器）
bash scripts/run-o-levels.sh        # 自动跑 6 档 × 3 次，输出表格 + 逐次 diff 结论

# Windows（本机，本次实测用的就是它）
gcc -O2 -o pivot_O2.exe pivot.c -lm
.\pivot_O2.exe .\uniformvector-2dim-5h.txt > stdout.txt
```

## 6. 附：wall 时间与程序自报时间的差值

| 档位 | wall (s) | 自报 (s) | 差 (s) | 差值来源 |
|---|---|---|---|---|
| `-O0` | 296.33 | 296.23 | 0.10 | 读文件 + 写 result.txt + 进程启动 |
| `-O1` | 32.78 | 32.68 | 0.10 | 同上 |
| `-O2` | 36.92 | 36.83 | 0.10 | 同上 |
| `-O3` | 33.71 | 33.61 | 0.10 | 同上 |

差值稳定在 0.1 s 左右，说明**计时函数包住的就是主循环**，符合手册"不得移动计时函数位置"的要求；同时也说明这套计时口径可靠（不是拿"启动+IO"凑出来的数）。
