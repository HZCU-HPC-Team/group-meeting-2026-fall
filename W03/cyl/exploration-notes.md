# W03 赛题实战与性能优化阶段总结

## 一、 赛题源码获取与环境准备

**1. 源码拉取**

* **遭遇问题**：尝试使用 `git clone git@github.com:...` 和 `git clone https://github.com/HZCU-HPC-Team/2022_IPCC.git` 两种方式拉取源码，均遭遇了网络超时报错（`Connection timed out`）。原因是学校超算服务器的网络环境受限，无法直接访问外部 GitHub。
* **解决方案**：采用 **本地中转法**。在本地电脑浏览器下载 `pivot.tar` 压缩包，通过 VS Code 直接拖拽上传至服务器，再使用 `tar -zxvf pivot.tar` 成功解压。
* **环境检查**：使用 `which gcc` 确认服务器已具备编译环境；通过 `gcc` 编译时添加 `-lm` 参数解决数学库链接问题。

## 二、 程序编译与基准结果验证

**1. 编译与运行**

* **命令**：`gcc -OX pivot.c -o pivot -lm`
* **运行**：`./time pivot uniformvector-2dim-5h.txt`。赛题程序默认不接受多个参数，只需输入一个数据文件即可。
* **结果对比**：程序输出结果自动保存至 `result.txt`。使用 `diff result.txt refer-2dim-5h.txt` 命令与标准答案进行对比。**结果：无任何输出，证明计算结果与赛题标准答案完全一致，程序跑通且准确无误。**

## 三、 编译优化实验（不改代码）

通过修改 GCC 编译选项，在保证结果正确的前提下，测试不同优化级别对程序性能的影响：

| 编译选项              | 第 1 次 (real) | 第 2 次 (real) | 第 3 次 (real) | 平均时间         | 加速比 (相对 -O0)     |
| :-------------------- | :------------- | :------------- | :------------- | :--------------- | :-------------------- |
| `-O0`               | 8m16.558s      | 8m15.083s      | 8m15.924s      | **495.8s** | **1.0x (基准)** |
| `-O1`               | 1m39.016s      | 1m37.500s      | 1m41.775s      | **99.0s**  | **4.99**        |
| `-O2`               | 1m14.763s      | 1m12.289s      | 1m17.748s      | **74.3s**  | **6.62**        |
| `-O3`               | 1m11.241s      | 1m12.223s      | 1m16.221s      | **73.23s** | **6.77**        |
| `-O3 -march=native` | 1m2.476s       | 1m30.358s      | 1m14.280s      | **75.70s** | **6.55**        |

* **实验结论**：`-O3` 结合 `-march=native` 效果最为显著。`-march=native` 让编译器针对当前服务器 CPU 的高级指令集进行深度定制，将原本需要 8 分多钟的计算压缩到了 1 分多钟，实现了 **6.55** 倍的性能飞跃。

## 四、 性能分析（perf 热点追踪）

**1. 整体体检 (`perf stat`)**

* **Cycles (CPU周期数)**：159,297,718,255
* **Instructions (指令数)**：912,842,391,704
* **内存受限指标 (topdown-mem-bound)**：3,763,747,706 (占比 0.4%)
* **Branch-misses (分支预测失败)**：63,221,228 (占比 0.04%)
* **研判分析**：从 `perf stat` 的数据看出，每周期执行指令数（IPC）为 **5.73**。这说明该程序是典型的**计算密集型**任务，CPU 一直在满负荷进行数学运算（`topdown-retiring` 占比达 88.6%）。

**2. 抓取热点 (`perf record` + `perf report`)**

* **耗时大户**：排在第一名的函数是 **`SumDistance`**，占比高达 99.51%。`main` 函数的 self 占比仅为 0.29%，但其 Children 占比高达 99.99%，说明 `main` 函数本身耗时极少，绝大部分时间都在循环调用 `SumDistance`。
* **采集环境与参数（详细记录）**：

  * **硬件环境**：HZCU 超算服务器（基于 x86_64 架构的高性能计算节点，单核主频约 2.60 GHz，具备大容量多级缓存）。
  * **软件环境**：Linux 系统（Ubuntu 内核），工作目录 `~/w03/code/pivot`。测试程序为基于 C 语言编写、使用 `gcc -O3 -march=native` 编译生成的 `pivot_O3_native` 可执行文件。
  * **网络与系统状态**：单人在局域网内 SSH 连接运行，测试期间服务器无其他高负载并发任务干扰，CPU 利用率稳定。
  * **核心命令**：`perf record -g ./pivot_O3_native uniformvector-2dim-5h.txt`
  * **关键参数解析**：
    * `-g`：开启调用栈（Call graph）记录。这非常关键，因为它不仅告诉我们 `SumDistance` 慢，还能通过调用图清晰地展示出是 `main` 函数调用了它。
    * `./pivot_O3_native`：经过最高级别优化（-O3 结合本机指令集）的可执行程序。
    * `uniformvector-2dim-5h.txt`：赛题提供的标准输入数据集。
  * **执行次数**：1 次。（注：为避免 perf 采样带来的额外开销干扰，热点抓取通常运行 1 次获取完整数据即可）。
  * **查看命令**：`perf report`（进入交互界面查看百分比排行，按 `q` 退出）。
* **AI 分析（为什么慢及优化思路）**：结合 perf 数据与代码分析，`SumDistance` 慢的根本原因是其算法复杂度极高（O(n^2)）且包含大量耗时运算。其一，代码使用了缓慢的 `pow(..., 2)` 求平方和 `sqrt()` 开根号；其二，双重嵌套循环导致所有点需全量比对，计算量达 25 万次以上；其三，函数每次调用都会用 `malloc` 重新分配内存并清零，带来额外开销。后续不改算法的优化方向包括：将 `pow` 替换为直接乘法，把 `malloc` 移到外层，或开启编译器的 `-ffast-math` 参数和 SIMD 向量化指令进一步压榨性能。
