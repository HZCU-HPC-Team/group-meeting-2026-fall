## 三、四个共性问题（按现场情况选讲）

**1. 测量不规范，数据不可比**

- 只跑一次；机器上还有别人在跑；没记录编译选项和输入文件；直接在终端看输出。
- 要求：跑前先看 `uptime` 确认负载；输出重定向到文件；至少 3 次取中位数；每次只改一个变量。

**2. 加速比算错**

- 加速比 = **基准耗时 / 新耗时**，基准必须是同一次实验里的 `-O0`。
- 常见错误：拿 `-O3` 的耗时当 `-O0`；换了输入文件还直接比；把 `1 - t/t0` 当成加速比。
- 组合评估速率 = 组合数 / 耗时，单位要写清楚（组/秒）。

**3. perf 数据读不懂**

- **IPC** = instructions / cycles。小于 1 说明 CPU 在等（访存、分支、依赖）；大于 1 说明一个周期能塞进多条指令。
- **cache-misses** 要看占总访存的比例，绝对值没有意义；不同机器之间不能横向比。
- **热点占比** = 该函数的采样数 / 总采样数。只看函数名不够，要能说出它被调用多少次、在哪一层循环里。
- perf 的数字是**证据**，不是**结论**。结论要写成"因为 A，所以 B"。

**4. 校验缺失**

- 换了编译选项、改了代码，必须重新 `diff result.txt refer-2dim-5h.txt`。
- **先对再快**：结果不对的加速比没有意义。

## 四、现场动手：删掉迭代日志（第一处优化）

**为什么从它开始**

W03 已经留了伏笔；改动小、风险低、不碰算法；效果直观，能立刻建立"优化 → 测量 → 验证"的闭环感。

**步骤**

1. 先测一次 baseline（`-O0`，输出重定向到文件），记下时间，作为基准；
2. 在 `pivot.c` 里找到打印迭代进度的那段输出（源码注释里标注了可删），删掉或注释掉；
3. 重新编译、运行，`diff` 一次——必须仍然一致；
4. 再测 3 次，取中位数，算加速比；
5. 讨论：为什么删几行 `printf` 会快这么多？

**边界（重要）**

- 只删"迭代进度"这类日志。`result.txt` 的写入、题目要求的输出、`Using time` 的打印都不动。
- 删完必须 `diff`。对不上就回退。
- 不要顺手改算法。今天的任务是"只做一处改动，并且证明它有效"。

**讨论要点**

- 每次 `printf` 都是一次（或多次）系统调用；输出到终端还要等终端渲染，重定向到文件则受缓冲区影响。
- 所以先确认：你的 baseline 是把输出重定向到文件测的，还是直接在终端测的？两者的基准不一样。

## 五、把标准动作固化成一张表

- 从今天起，每次实验都填第二节那张表。
- 这张表有三个用处：① 自己的实验可复现；② 组会上能讲清楚；③ 学期末写报告时直接连起来就是结果表。
- 六步标准动作再念一遍：**环境检查 → 编译 → 运行 → 正确性校验 → 测量 → 记录**。
- 今天补一条：**改动 → 重新校验 → 重新测量 → 重新记录**。改完不测等于没改。
