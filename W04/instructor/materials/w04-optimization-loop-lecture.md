## 一、承上：W03 留下了什么

- W03 做了三件事：跑通 pivot、比较编译选项、用 perf 采数据。
- **编译选项是"不改代码的优化"**，今天的重点是"改代码的优化"。
- perf 不是作业，是**证据**。没有 perf 数据就动手改代码，等于蒙眼走路。
- 所以今天的第一道门槛是数据：`perf stat` 有四个计数，`perf record` 有热点函数和占比。拿不出来的人，先补齐。

> 补齐不是惩罚。现场找已经跑通的同学结对，讲师同时协助，15 分钟内把 baseline 数据跑出来。

## 二、把 perf 数据变成图

### 2.1 先确认数据够不够

| 需要的东西 | 怎么来 | 用途 |
|---|---|---|
| 四个计数 | `perf stat ./pivot_O0 <input>` | 判断计算密集 / 访存密集 |
| 热点函数与占比 | `perf report --stdio` | 画热点图 |
| 调用关系（选做） | `perf record -g` + 火焰图 | 看是谁调用了热点 |
| 耗时基线 | `time` 或程序自报，3 次取中位数 | 算加速比 |

- 只有 `perf record` 带 `-g` 才有调用栈；之前没带的人，重跑一次 `perf record -g`。
- 火焰图里出现 `unknown` 或 `[unknown]`，要说明原因（缺符号 / 没采到栈），不要装作没看见。

### 2.2 三张图，各回答一个问题

**图一：热点条形图（人人要做）**

- 横轴 = 耗时占比（%），纵轴 = 函数；
- 数据来源：`perf report --stdio` 的 Overhead 列；
- 回答：**时间花在谁身上？**
- 要求：图上标出采样总数、采集命令、机器。

**图二：火焰图（选做，需要调用栈）**

- 横轴越宽越耗时，纵向是调用栈，**不是时间轴**；
- 回答：**是谁调用了它？它在哪一层？**
- 拿不到调用栈就说明原因，不强行做。

**图三：前后对比图（迭代用，最重要）**

- 横轴 = 版本（baseline → v1 → v2…），纵轴 = 同一输入下的耗时；
- 数据来自你的迭代表；
- 回答：**这次改动值不值？下一轮该往哪走？**

> 前两张图解释"为什么慢"，第三张图记录"你做了什么、有没有用"。没有第三张，优化就只是一次性体验。

### 2.3 读图三问

1. 最大的一块是谁？占多少？
2. 它在调用栈的哪一层？被谁调用、调用多少次？
3. 这块时间更像计算、访存、分支、I/O 还是系统调用？依据是 `perf stat` 里的哪个数？

答不出第三问，说明还没到能动手的程度。

### 2.4 工具与边界

- 可以把 `perf report --stdio` 的文本交给 AI 整理成表格或图，但**数据必须是你自己采的**，图和数字要对得上。
- 图必须标单位和样本数；不要为了好看删掉占比小的项。
- 图不是结论。结论要写成"因为 A，所以 B，我打算改 C"。

## 三、从图到假设：做一轮真正的优化

### 3.1 先写假设，再改代码

每轮动手前，先写出一句话：

> 因为 perf 显示 `X` 占 `Y%`，且 `perf stat` 显示 `Z`，所以我猜瓶颈是 `…`，打算改 `…`，预期 `…`。

写不出这句话，就不要改。改完发现假设错了，也是有效结果——记录下来，说明为什么错。

### 3.2 用 AI 的正确姿势

- **先解释，后动手**：让 AI 先解释热点为什么慢、可能属于哪类问题，再让它列 3 个候选改法（预期收益 / 风险 / 改动范围），你来选一个。
- **一次只改一处**：不要让 AI 重写整个文件；diff 要小到你能逐行读懂。
- **AI 的话只是假设**：它说"能快 10 倍"不算数，唯一裁判是你自己的测量。
- **让它帮你查正确性**：浮点运算顺序、输出格式、边界条件——这三处最容易改快但改错。

### 3.3 按自己的数据选方向（不按固定顺序）

| 现象 | 可能的原因 | 第一步尝试 |
|---|---|---|
| 热点在 I/O、`write`、`printf` | 日志 / 调试输出太多 | 删掉或减少非必要输出 |
| 热点在同一个函数、指令数很高 | 循环里重复计算 | 把循环不变量提到外面、缓存中间结果 |
| `cache-misses` 占比高 | 访存不连续、重复读 | 调整访问顺序、减少重复读取 |
| `branch-misses` 高 | 分支难预测 | 减少循环内的条件判断 |
| 以上都不明显 | 单核已经到顶 | 编译选项（对照）或考虑并行（W05） |

- 编译选项放到最后作为对照，不作为主要手段：它不是你这次要练的能力。
- 真正的算法重写和并行化放 W05。今天的目标是**小步、可验证、可回退**。

### 3.4 验证与测量（每轮都做）

1. 重新编译；
2. `diff result.txt refer-2dim-5h.txt`，必须一致；
3. 至少 3 次测量，取中位数；
4. 算相对上一版和相对 baseline 的加速比；
5. 填进迭代表。

结果对不上就回退，不要"修一修再看看"。没变快也要记录，并写下你的解释。

## 四、版本迭代管理：让每次改动可追溯

### 4.1 Git 层面的三条规矩

```bash
# 1. 在跑通且 diff 一致的版本上打基线
git tag v0-baseline

# 2. 一次改动一个 commit，提交信息带数据
git commit -m "opt: remove iteration logs | -O0 | 132.4s -> 41.7s | diff ok"

# 3. 失败的尝试用 revert 回退，不要手动改回去
git revert <commit>
```

- 为什么要带数据：三个月后回看，commit message 就是最小可复现记录。
- 为什么用 `revert`：手动改回去会丢掉"我试过、失败了"这段历史，而这段历史恰恰有价值。

### 4.2 迭代表（`iterations.md`）

| 版本 | commit | 改动 | 编译选项 | 次数 | 中位数耗时 | 相对上一版 | 相对 baseline | diff | 结论 |
|---|---|---|---|---|---|---|---|---|---|
| v0-baseline | | 原始代码 | -O0 | 3 | | — | 1.00x | ok | 基准 |
| v1 | | | | 3 | | | | | 保留 / 回退 |

**一个原则：看这张表就能复现一次实验。** 缺一项，就算没记录。

### 4.3 大文件不进仓库

- 输入数据、`result.txt`、`run.log` 不进 git；
- 只提交迭代表、图、说明和代码改动；
- 需要引用数据时写文件名和规模，不要提交原文件。

## 五、现场演示：一轮完整迭代

以"删掉迭代日志"为例，但**先看 perf 是否支持这个判断**：

1. 在 baseline 上打 `v0-baseline`；
2. 看热点图，提出假设（I/O / 日志占比多少）；
3. 问 AI 要候选改法，自己选一个；
4. 改一处，commit（消息带数据）；
5. 重新编译 → `diff` → 测 3 次；
6. 填迭代表、更新前后对比图；
7. 如果没变快，现场演示 `git revert`，并把这次失败填进表里。
